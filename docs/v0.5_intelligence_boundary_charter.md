# v0.5 Intelligence Boundary Charter

**Status**: Active (v0.5)
**Date**: January 2026
**Type**: Architectural Boundary Definition
**Dependency**: PR34 (v0.4 Confidence Release Declaration)

---

## Core Declaration

```
v0.4 explains.
v0.5 decides.

v0.4 becomes history.
v0.5 chooses the future.

These layers never merge.
This boundary cannot be crossed.
```

---

## 1. Purpose

v0.4 Confidence is **complete, frozen, and immutable**.

v0.5 introduces **Intelligence**: learning, optimization, and adaptive decision-making.

This charter exists to ensure that v0.5 evolution **never violates v0.4 immutability**.

### The Core Principle

```
v0.4 Confidence = Immutable Explanation Layer
v0.5 Intelligence = Evolving Decision Layer
```

These are **not the same thing**.
They do **not mix**.
They do **not modify each other**.

---

## 2. Responsibilities (Separation of Concerns)

### v0.4 Confidence (Existing, Frozen)

**What it is:**
- Immutable explanation snapshot
- Auditable historical record
- Non-numeric, non-evaluative description
- Fixed structure, frozen vocabulary
- Version + timestamp provenance

**What it does:**
- Generates `confidence_reason` from observation
- Logs reason + version + timestamp
- Never changes after generation
- Never influenced by future models or optimization

**What it does NOT do:**
- Does not make decisions
- Does not optimize
- Does not learn
- Does not judge correctness
- Does not predict outcomes

### v0.5 Intelligence (Future, Adaptive)

**What it is:**
- Adaptive decision-making layer
- Learning-capable optimization
- Future-facing intelligence
- Evolving models and strategies

**What it does:**
- Makes decisions based on multiple inputs
- Learns from outcomes
- Optimizes behavior over time
- Adapts to changing market conditions

**What it does NOT do:**
- Does not regenerate v0.4 `confidence_reason`
- Does not modify v0.4 vocabulary or structure
- Does not reinterpret past v0.4 snapshots
- Does not treat v0.4 as mutable state

---

## 3. Hard Boundary (Prohibited Actions)

### v0.5 Intelligence SHALL NEVER:

1. **Regenerate v0.4 confidence_reason**
   - Once logged, `confidence_reason` is permanent
   - v0.5 cannot "fix" or "improve" past reasons
   - Historical snapshots remain unchanged

2. **Reinterpret v0.4 semantics**
   - v0.4 vocabulary meanings are frozen
   - v0.5 cannot change what "temporal indicators present" means
   - PR30 vocabulary charter is immutable

3. **Modify v0.4 structure**
   - 4-section format is permanent (PR27)
   - v0.5 cannot add fields to `confidence_reason`
   - v0.5 cannot change section order or separators

4. **Provide feedback to v0.4**
   - v0.5 cannot say "this confidence_reason was wrong"
   - v0.5 cannot tune v0.4 generation based on outcomes
   - v0.4 generation logic is READ-ONLY

5. **Use v0.4 as training signal**
   - v0.5 cannot directly optimize against `confidence_reason` correctness
   - v0.4 is explanation, not ground truth
   - `confidence_reason` is not a label for supervised learning

6. **Evaluate v0.4 quality**
   - v0.5 cannot score "how good" a `confidence_reason` is
   - v0.4 is description, not assessment
   - Quality metrics do not apply to immutable snapshots

### Why These Are Prohibited

Each prohibition protects v0.4 immutability:

- **Regeneration** breaks provenance (reason + version + timestamp)
- **Reinterpretation** breaks audit stability
- **Modification** breaks frozen vocabulary/structure
- **Feedback** breaks immutability (implies v0.4 can change)
- **Training signal** treats v0.4 as optimization target (wrong layer)
- **Quality evaluation** treats explanation as judgment (category error)

## 4. Permitted Actions (Read-Only Consumption)

### v0.5 Intelligence MAY:

1. **Read confidence_reason as context**
   - Use `confidence_reason` as one input among many
   - Consider observation context alongside other signals
   - Never modify or regenerate

2. **Display confidence_reason in UI**
   - Show `confidence_reason` to users for transparency
   - Present as historical explanation, not current assessment
   - Include version + timestamp for provenance

3. **Use confidence_reason in audit/analysis**
   - Analyze patterns in historical `confidence_reason` logs
   - Visualize explanation trends over time
   - Support post-hoc investigation

4. **Quote confidence_reason in reports**
   - Include `confidence_reason` in human-readable summaries
   - Cite as explanation of system state at time T
   - Never present as prediction or recommendation

### Consumption Pattern

```python
# ✓ ALLOWED: Read-only reference
past_reason = log_row["confidence_reason"]  # Historical context
past_version = log_row["confidence_reason_version"]  # Provenance
past_timestamp = log_row["confidence_reason_generated_at"]  # When

# Use as one input among many (read-only)
intelligence_decision = v0_5_intelligence(
    current_state,
    past_reason,  # Context only, not modified
    other_signals
)

# ✗ PROHIBITED: Modification or regeneration
# past_reason = regenerate(past_reason)  # NEVER
# past_reason = improve(past_reason)  # NEVER
# new_reason = optimize_based_on_outcome(past_reason)  # NEVER
```

## 9. Rationale

### Why This Boundary Exists

1. **Audit Integrity**
   - Immutable v0.4 ensures audit trail is trustworthy
   - Historical records cannot be "improved" retroactively
   - Legal/compliance documentation remains stable

2. **Provenance Guarantee**
   - `confidence_reason` + version + timestamp = complete provenance
   - v0.5 cannot break this guarantee
   - Future cannot rewrite past

3. **Layer Separation**
   - Explanation (v0.4) and Decision (v0.5) are different concerns
   - Mixing them creates unclear responsibility
   - Separation enables independent evolution

4. **Reproducibility**
   - v0.4 snapshots are reproducible forever
   - v0.5 changes do not affect historical v0.4 behavior
   - Past explanations remain valid under v0.4 spec

### Why Not Merge?

**Question**: Why not let v0.5 generate better `confidence_reason`?

**Answer**: Because that breaks immutability:
- v0.4 is historical record, not work-in-progress
- Audit requires stable past, not evolving reinterpretation
- v0.5 can generate its own explanations (in new fields)

## 11. Non-Goals

This charter does NOT:

1. Define v0.5 intelligence algorithms
2. Specify learning methods or optimization strategies
3. Design how v0.5 makes decisions
4. Constrain v0.5 evolution (only constrains v0.4 interaction)
5. Modify any v0.4 specifications

v0.5 is free to evolve — **except where it touches v0.4**.

## 12. Enforcement

### Violation Detection

Any of these indicates boundary violation:
- v0.5 PR modifies v0.4 builder code
- v0.5 PR changes v0.4 vocabulary or structure
- v0.5 PR regenerates historical `confidence_reason`
- v0.5 PR treats v0.4 as optimization target

### Consequence

Boundary violations are **blocking issues**:
- PR must be rejected
- Design must be reconsidered
- Alternative approach required (new fields, not v0.4 modification)
