## 1. Purpose

v0.4 Confidence established **immutable explanation history**:
- Fixed structure (PR27)
- Frozen vocabulary (PR30)
- Compliance detection (PR31-32B)
- Snapshot metadata (PR33)
- Official release declaration (PR34)

v0.5 Intelligence introduces **adaptive decision-making** (learning, optimization, evolution).

To maintain audit integrity, **decisions must also become immutable history**.

### Why Decision Records?

Without decision records:
- Intelligence decisions are invisible
- Judgments cannot be audited
- Responsibility is unclear
- Post-hoc rationalization is possible

With decision records:
- Every decision is logged at the moment it occurs
- Judgments are auditable forever
- Responsibility is explicit
- History cannot be rewritten

**PR38 defines Decision Records as the immutable history of v0.5 Intelligence judgments.**

---

## 2. Decision Record Definition

### What is a Decision Record?

A **Decision Record** is an immutable snapshot of:
- **What** action was decided
- **Why** it was decided (reasoning)
- **Which inputs** informed the decision
- **When** it was decided (timestamp)
- **Which version** of intelligence generated it

### What Decision Records Are NOT

Decision Records are **not**:
- Model parameters or weights
- Training checkpoints
- Performance scores or evaluations
- Predictions or forecasts
- Mutable state

Decision Records **are**:
- Historical snapshots of judgments
- Human-readable audit trails
- Non-numeric explanations of decisions
- Immutable once logged
- Version-stamped provenance

## 3. Required Fields (Logical Specification)

**NOTE**: This is a logical specification. PR38 does not implement these fields (Docs Only).

```json
{
  "decision_action": "<action_taken>",
  "decision_reason": "<human_readable_explanation>",
  "decision_inputs": ["<input_key_1>", "<input_key_2>", "..."],
  "decision_version": "v0.5",
  "decision_generated_at": "<UTC_ISO8601_timestamp>"
}
```

### Field Requirements

#### `decision_action` (string, required)

**Definition**: The action decided by v0.5 Intelligence.

**Examples**:
- `hold_position`
- `increase_exposure`
- `reduce_risk`
- `exit_market`
- `wait_for_stability`

**Requirements**:
- Non-empty string
- Describes the action taken, not the outcome
- Present tense or imperative form

**Prohibited**:
- Empty string (every decision must name an action)
- Numeric scores (use descriptive names)
- Evaluative terms like "good_action" or "bad_action"

---

#### `decision_reason` (string, required)

**Definition**: Human-readable explanation of why the decision was made.

**Purpose**: Explains the intelligence layer's reasoning at the moment of decision.

**Examples**:
- `market volatility below stability threshold, intent aligned with regime`
- `confidence snapshot indicates temporal continuity, increasing exposure justified`
- `regime transition detected, reducing position size as constitutional precaution`

**Requirements**:
- Non-empty string
- Human-readable prose (not code or structured data)
- Explains "why" not "what" (action is in `decision_action`)
- Written at moment of decision (not post-hoc)

**Relationship to v0.4 confidence_reason**:
- Different purpose: `confidence_reason` explains observation state, `decision_reason` explains judgment
- Different layer: v0.4 vs v0.5
- Can reference v0.4 as context but never replaces or modifies it
- Both are immutable, both are auditable

---

#### `decision_inputs` (array of strings, required)

**Definition**: List of input keys from PR36 allowlist that informed this decision.

**Purpose**: Declares which inputs were used (contract compliance + audit trail).

**Requirements**:
- Array of strings (may be empty if no inputs)
- All keys must be in PR36 allowlist (Category A/B/C)
- Keys are literal field names, not values
- Sorted alphabetically (stable ordering)

**Examples**:
```json
["confidence_reason", "entropy_bp", "intent_primary", "price", "regime", "volatility"]
```

**Contract Enforcement**:
- PR37 guard validates all keys are in allowlist
- Undeclared keys trigger compliance warnings
- Empty array is valid (decision without external inputs)

---

#### `decision_version` (string, required)

**Definition**: Version identifier for the intelligence specification that generated this decision.

**Value**: Fixed string `"v0.5"` for PR38.

**Purpose**: Locks semantics of decision to specification version (same principle as PR33 `confidence_reason_version`).

**Requirements**:
- Non-empty string
- Fixed to `"v0.5"` in this charter
- Enables future evolution (v0.6+) without breaking historical record interpretation

---

#### `decision_generated_at` (string, required)

**Definition**: UTC timestamp when decision was generated.

**Format**: ISO-8601 UTC (e.g., `"2026-01-10T15:32:45.123456Z"`)

**Purpose**: Immutable provenance timestamp (same principle as PR33 `confidence_reason_generated_at`).

**Requirements**:
- Non-empty string
- Valid ISO-8601 UTC format
- Generated at moment of decision (not logged later)
- Monotonically increasing for sequential decisions

## 4. Relationship to v0.4 Confidence

### Two Histories, One System

```
v0.4 Confidence Record (Explanation):
- What was observed
- How state appeared
- Which signals were present
- READ-ONLY snapshot

v0.5 Decision Record (Judgment):
- What action was taken
- Why action was chosen
- Which inputs informed judgment
- READ-ONLY snapshot
```

### Boundary Rules (Strict)

v0.5 Decision Records **MAY**:
- Reference v0.4 `confidence_reason` as context (READ-ONLY)
- Include `confidence_reason` in `decision_inputs` list
- Quote v0.4 explanation in `decision_reason` text
- Display v0.4 and v0.5 records side-by-side in UI

v0.5 Decision Records **SHALL NEVER**:
- Regenerate v0.4 `confidence_reason`
- Reinterpret v0.4 semantics
- Modify v0.4 structure or vocabulary
- Evaluate v0.4 correctness
- Use v0.4 as training label
- Provide feedback to v0.4 generation

**These prohibitions are defined in PR35 (Boundary Charter) and enforced by PR37 (Compliance Guard).**

## 5. Prohibited Actions (Hard Rules)

### v0.5 Decision Records SHALL NEVER:

#### Ban 1: Regenerate Past Decisions

```python
# ✗ PROHIBITED
def improve_past_decision(historical_log, new_model):
    for row in historical_log:
        old_decision = row["decision_action"]
        old_reason = row["decision_reason"]

        # ✗ Regenerating decision with better model
        new_decision = new_model.decide(row["state"])  # NEVER
        new_reason = new_model.explain(row["state"])  # NEVER

        row["decision_action"] = new_decision  # NEVER
        row["decision_reason"] = new_reason  # NEVER
```

**Why prohibited**: Decision Records are historical snapshots. Regeneration breaks provenance.

---

#### Ban 2: Post-Hoc Rationalization

```python
# ✗ PROHIBITED
def justify_past_decision(decision_record, outcome):
    # ✗ Rewriting decision_reason based on outcome
    if outcome == "good":
        decision_record["decision_reason"] = "correctly anticipated market movement"  # NEVER
    else:
        decision_record["decision_reason"] = "prudent risk management given uncertainty"  # NEVER
```

**Why prohibited**: `decision_reason` must be written at moment of decision, not after outcome is known.

---

#### Ban 3: Evaluate Decision Correctness

```python
# ✗ PROHIBITED
def evaluate_decision_quality(decision_record, outcome):
    decision_action = decision_record["decision_action"]

    # ✗ Judging whether decision was "right" or "wrong"
    if outcome > expected:
        quality = "good decision"  # NEVER
    else:
        quality = "bad decision"  # NEVER

    return quality  # Decision Records are not evaluated
```

**Why prohibited**: Decision Records are history, not training labels. Evaluation is a category error.

---

#### Ban 4: Use as Training Label

```python
# ✗ PROHIBITED
def train_on_decisions(historical_log):
    for row in historical_log:
        decision_action = row["decision_action"]
        outcome = row["actual_outcome"]

        # ✗ Treating decision as supervised learning target
        loss = measure_decision_accuracy(decision_action, outcome)  # NEVER
        model.optimize(loss)  # NEVER
```

**Why prohibited**: Decision Records are explanations, not ground truth. v0.5 can learn from outcomes, but not by treating Decision Records as labels.

---

#### Ban 5: Modify Historical Records

```python
# ✗ PROHIBITED
def normalize_decision_format(historical_log):
    for row in historical_log:
        # ✗ Modifying past decision_reason to match new format
        old_reason = row["decision_reason"]
        new_reason = reformat_to_new_standard(old_reason)  # NEVER
        row["decision_reason"] = new_reason  # NEVER
```

**Why prohibited**: Historical records are immutable. Format changes apply only to future decisions.

---

#### Ban 6: Feedback to v0.4

```python
# ✗ PROHIBITED
def improve_confidence_based_on_decisions(historical_log):
    for row in historical_log:
        decision_quality = evaluate_decision(row)  # Already prohibited (Ban 3)
        confidence_reason = row["confidence_reason"]  # v0.4 field

        # ✗ Tuning v0.4 based on v0.5 decision outcomes
        if decision_quality == "good":
            improve_confidence_generation(confidence_reason)  # NEVER
```

**Why prohibited**: v0.4 is frozen (PR34). v0.5 decisions cannot modify v0.4 generation.

## 8. Enforcement

### Design Time

- PR38 is the reference for all v0.5 Decision Record implementations
- Any code that regenerates or modifies Decision Records is rejected
- Post-hoc rationalization is prohibited
- Decision Records must be written at moment of decision

### Implementation Time

- Decision Records logged immediately after decision
- No modification after logging
- Version and timestamp required for all records
- Input keys validated against PR36 allowlist (PR37 guard)

### Review Time

- Code review verifies immutability of Decision Records
- Any regeneration or modification is blocking issue
- Post-hoc rationalization detected and rejected
- Training on Decision Records as labels is prohibited

## 9. Examples: Compliant Decision Recording

### Example 1: Simple Decision Record

```python
# ✓ ALLOWED: Immutable decision recording
def make_and_record_decision(current_state, historical_log):
    # Generate decision at time T
    decision_action = intelligence_model.decide(current_state)
    decision_reason = intelligence_model.explain(current_state)
    decision_inputs = list(current_state.keys())

    # Create immutable Decision Record
    decision_record = {
        "decision_action": decision_action,
        "decision_reason": decision_reason,
        "decision_inputs": sorted(decision_inputs),  # Alphabetically sorted
        "decision_version": "v0.5",
        "decision_generated_at": datetime.utcnow().isoformat(),
    }

    # Log immediately (never modify after this)
    log_decision(decision_record)

    return decision_record
```

## 13. Positioning (Why This Matters)

### Dual Accountability

Meridian maintains two immutable histories:

**v0.4 Confidence (Explanation)**:
- "Why did we see the market this way?"
- Observation state description
- Non-numeric, non-evaluative
- READ-ONLY snapshot

**v0.5 Decision (Judgment)**:
- "Why did we take this action?"
- Intelligence judgment rationale
- Human-readable reasoning
- Immutable record

Together, they provide:
- Complete audit trail (state + action)
- Legal defensibility (historical provenance)
- Reproducibility (version + timestamp)
- Accountability (no hidden judgments)

### Why Not Merge?

**Question**: Why not merge `confidence_reason` and `decision_reason` into one field?

**Answer**: Different purposes, different layers:
- `confidence_reason` explains **what was observed**
- `decision_reason` explains **what was decided**
- Observation ≠ Judgment
- v0.4 (frozen) ≠ v0.5 (adaptive)

Separation enables:
- Independent evolution
- Clear responsibility boundaries
- Audit integrity
